# 长任务与多 Agent 工作交接 Context Runtime 长报告设计

## 目标

产出一份可独立阅读的中文长报告，并发布到用户的语雀空间。报告同时服务于三类用途：

1. 作为 PowerContext 后续研究与工程讨论的共同基线；
2. 给出跨执行阶段、同构多 Agent 和异构多 Agent 工作交接的可实现架构、可观测性体系与 MVP 路线；
3. 为后续工业论文或研究论文提炼研究问题、实验假设和评价指标。

报告不是对前序 ChatGPT 对话的简单扩写。它应结合当前仓库已经确立的产品定位与技术抽象，区分既有事实、候选设计和待验证假设。

报告的顶层研究对象是“工作连续性”，不是某一种 Agent 拓扑。只要工作跨越了不能直接共享完整运行状态的执行边界，就会产生上下文交接问题。该边界既可能位于两个不同模型之间，也可能位于同一种 Agent 的两个实例之间，还可能位于同一个逻辑 Agent 因上下文窗口、会话中断或阶段切换而产生的前后两段执行之间。

## 标题与形式

拟定标题：

> 面向长任务与多 Agent 工作交接的 Context Runtime：研究框架、系统设计与评测方法

首版采用一篇完整长报告，目标篇幅为 12,000–18,000 字。定稿后可以拆分为问题与愿景、Runtime 架构、可观测性、评测方法四篇系列文档。

## 目标读者

- 正在构建 Agent 基础设施的工程师与架构师；
- 需要在单 Agent 长任务、同构 Agent 集群或 Codex、Claude Code 等异构 Agent 之间维持工作连续性的研发团队；
- 希望从真实工程系统中提炼工业论文或学术问题的研究人员；
- PowerContext 的产品、研发与评审参与者。

## 核心论点

报告围绕以下可证伪命题展开：

1. 长任务的主要瓶颈不只是上下文窗口长度，还包括上下文选择、传播、版本、一致性和跨执行边界的恢复。
2. 跨执行实例的上下文可以被建模为受治理的工作状态与交接制品，而不是执行实例之间复制的 Prompt。
3. Context Runtime 应提供来源、制品、视图、版本、血缘、冲突、失效和反馈等生命周期能力。
4. Context Runtime 应同时服务三类核心场景：单 Agent 自我接力、同构多 Agent 交接和异构多 Agent 交接；异构性是需要专项验证的变量，而不是产品成立的前提。
5. 不同执行实例不需要共享完整内部状态，但需要通过开放边界共享可追溯的 handoff context。
6. Context Runtime 的价值必须同时由任务结果、交接效率、上下文质量和运行成本来衡量。

这些命题在报告中不得写成已经得到实验证明的结论。Context Graph、Git 式版本管理和共享世界模型均作为候选设计或分析隐喻呈现。

报告采用两层术语：

- **逻辑 Agent**：从用户或任务视角持续承担同一角色的 Agent；
- **执行实例（execution episode/worker）**：具有有限上下文窗口、独立会话状态和明确起止边界的一段实际执行。

单 Agent 自我接力在逻辑上仍是一个 Agent，在运行时上则跨越了多个不能直接共享完整状态的执行实例，因此与多 Agent handoff 共享同一组基础设施问题。报告不把它描述成传统的并行多 Agent 协同。

## 与 PowerContext 现状的关系

报告以仓库当前产品定义为约束：

- PowerContext 的产品中心是人和 Agent 共同推进的工作，以及工作能否被理解、接手和继续；
- Source 是外部工作证据，Artifact 是可维护的上下文制品，Trigger 是影响制品生命周期的外部信号；
- Handoff context 是面向接手者的视图，不是全量日志或完整知识库；
- 原始数据仍由外部系统持有，PowerContext 不取代代码仓库、工单、文档或遥测系统；
- 个人状态与团队资产需要分层，不能把所有 Agent 的内部状态无条件合并。

长报告可以提出超出现有实现的研究架构，但必须明确标记“当前能力”“候选扩展”和“长期研究方向”。

## 报告结构

### 1. 执行摘要

用两页以内说明问题、核心主张、建议架构、评测方法和近期行动。

### 2. 问题定义

解释长上下文窗口为何不能自动解决长任务问题，区分上下文容量、相关性、时效性、一致性和可追溯性。

### 3. 跨执行实例的上下文失效模式

建立跨执行实例的失效模式分类：上下文分裂、事实漂移、重复探索、错误传播、版本错配、隐式冲突、过度共享和权限泄露。指出其中哪些同时适用于单 Agent 自我接力，哪些主要由并行协同产生。

### 4. Context Runtime 核心抽象

定义 Work、Source、Artifact、Context Item、Context View、Trigger、Handoff、Revision、Evidence 和 Feedback 的职责及关系。

### 5. 工作连续性与多 Agent 交接架构

先给出与宿主和拓扑无关的执行实例交接架构，再分别说明三种部署形态：

1. 单 Agent 因上下文窗口、会话中断或阶段切换进行自我接力；
2. 多个同构 Agent 之间进行串行交接或并行协作；
3. Codex、Claude Code 或其他异构 Agent 通过 adapter、source capture、artifact projection 和 handoff protocol 协作。

避免假设可以读取或复制宿主 Agent 的私有提示词、认证信息或完整内部状态。

### 6. 生命周期、版本与一致性

讨论上下文的创建、更新、引用、派生、合并、冲突、失效、归档和删除。给出 Context Graph 与线性日志、事件流、文档制品等实现选择的对比。

### 7. 可观测性

定义 context span/event、lineage、消费、引用、决策影响、传播延迟、漂移、冲突、冗余、成本和敏感数据边界。区分可直接观测信号和只能通过代理指标估计的“影响”。

### 8. 公开 Benchmark 调研

核验并比较公开基准的权威来源、任务类型、上下文长度、是否原生多 Agent、过程可观测性、可复现性和工程成本。不得因前序对话提到某一名称就默认其存在、成熟或适用。

### 9. 实验设计

至少包含：

- 单执行实例、单 Agent 自我接力、同构多 Agent 和异构多 Agent 的架构对照；
- 无共享、摘要交接、检索共享、版本化 handoff 等机制消融；
- 不同任务长度、Agent 数量、上下文预算和冲突率下的压力测试；
- 任务质量、时间、Token/费用、重复工作、漂移、交接保真度和恢复能力指标；
- 对泄漏、错误上下文和过期上下文的鲁棒性测试。

实验不得把“单 Agent”只当作一个无需交接的基线。至少设置以下场景：

- 单实例在上下文窗口内完成任务；
- 单 Agent 使用宿主默认压缩或摘要继续任务；
- 单 Agent 使用结构化 Handoff 启动新的执行实例；
- 同构 Agent 使用结构化 Handoff；
- 异构 Agent 使用结构化 Handoff。

这样可以分别估计 Context Runtime 的通用收益、并行协作成本和跨宿主语义损失。

### 10. PowerContext MVP 与路线

给出 0–3 个月、3–6 个月和 6–12 个月的工程路线。近期 MVP 聚焦可追溯 handoff、显式读取/写入、基础检索和测量闭环，不把完整知识图谱或自动冲突解决作为前置条件。

### 11. 研究问题与论文方向

把系统贡献拆成可回答的问题，并说明适合工业论文、系统论文或经验研究的证据要求。

### 12. 风险、局限与开放问题

覆盖因果归因困难、宿主 Agent 可观测性有限、评测污染、隐私、权限、跨模型语义损失、标准缺失和维护成本。

### 13. 结论与下一步

给出可以直接进入项目排期的近期行动，以及仍需通过原型或实验决定的设计分叉。

## 证据与引用策略

- Benchmark、论文、产品能力和接口限制优先引用论文、官方仓库、官方文档或维护者发布的一手材料。
- 对时间敏感的 Codex、Claude Code 等产品能力，在写作时重新核验。
- 产业观点和综合判断标记为“本文判断”或“设计假设”。
- 不使用无法定位出处的精确数字。
- 引用集中维护，同时在正文关键论断附近给出链接或脚注。

## 图表设计

报告包含 3–5 个 Mermaid 图：

1. 从 Prompt 传递到 Context Runtime 的范式变化；
2. Source、Artifact、Trigger、View 与 Agent 的关系；
3. 单 Agent 自我接力、同构交接与异构交接的统一执行实例 handoff 数据流；
4. Context lineage 与 revision/merge/conflict 模型；
5. 指标体系或实验矩阵。

图表必须帮助解释数据流、生命周期或实验变量，不能只作装饰。

## 验收标准

本地报告和语雀版本都必须满足：

- 报告能够脱离原聊天记录独立阅读；
- 关键概念与仓库现有产品定义不冲突；
- 顶层定位不把 PowerContext 限定为异构 Agent 基础设施；
- 明确定义逻辑 Agent、执行实例和自我接力，并与传统并行多 Agent 协同区分；
- 同构、异构和单 Agent 自我接力均有对应的架构说明与实验设计；
- 当前实现、候选设计、研究假设三者标识清楚；
- 所有公开 Benchmark 均有可核验的一手来源；
- 至少给出一套可执行的 MVP、事件模型、核心指标和对照实验；
- 语雀页面标题、目录、代码块、表格、引用和 Mermaid 图可正常阅读；
- 发布完成后重新打开页面检查内容没有截断或格式破坏。

## 发布约定

优先发布到用户已登录语雀账号中最近使用或个人知识库内。若存在多个无法判断的团队知识库，或当前账号没有创建权限，则停在选择知识库这一步请用户指定；不得擅自向公开或团队空间发布。

本地报告作为源文件保存在仓库文档目录，语雀是发布视图。后续修订应先更新本地源文件，再同步语雀，避免形成两个无法判断权威性的版本。
